## Remaining weaknesses, in priority order

| Priority | Finding and evidence | Recommended next action |
|---|---|---|
| **P0: real-user release blocker** | Owner routes have no caller authentication. [guard.ts](../web/src/lib/server/guard.ts) calls `getOwnerUser()`, which selects the first global owner in [data.ts](../web/src/lib/server/data.ts). A separate client with no credentials received 200 from `/api/summary` in local reproduction. `/api/reset` also has no authentication and resets all owners. | Keep the public app restricted to synthetic demo use until authenticated, per-user ownership is implemented and cross-client read/write/reset tests pass. A browser UI gate is insufficient. |
| **P1: durable storage** | [db.ts](../web/src/lib/db.ts) defaults to per-instance `/tmp` SQLite on serverless hosts. State can disappear on cold starts or disagree across instances. Uniform route configuration does not guarantee one shared disk across horizontally scaled instances. | Configure and verify durable libSQL/Turso storage before real use; add restart and multi-instance persistence tests. The code already supports the adapter. |
| **P1: prediction consistency** | Main owner screens use [compute.ts](../web/src/lib/server/compute.ts): rule-based safe-to-spend plus a synthetic logistic risk model from [ml.ts](../web/src/lib/engine/ml.ts). The v1 persona routes use the shipped LightGBM path forecaster. v1 chat separately uses rule/bootstrap calculations. Therefore model claims and values can differ between surfaces. | Clearly identify each model in the demo and documentation; later unify serving through one forecast/context builder with explicit method/version fields. Avoid claiming every visible budget is produced by LightGBM. |
| **P1: unused declared inputs** | `incomeDay`, `rentAmountTaka` and `rentConfirmed` are accepted and stored by [userInputs.ts](../web/src/lib/server/userInputs.ts), but are not consumed by the owner financial compute pipeline. | Wire these declarations into timing/commitment calculations with regression tests, or state clearly that they do not yet affect those projections. |
| **P1: AI guardrail semantics** | Main Copilot now checks all supported numeric representations, but it still uses an allowlist rather than the slot protocol used by the v1 orchestrator. Number existence alone does not prove the correct unit, label or meaning; slot rendering also cannot verify a model's qualitative advice. | Unify narration through typed facts/slots and add adversarial tests for swapped balances/budgets, units, unsupported advice and unsupported certainty. Keep deterministic fallback enabled. |
| **P1: evaluation provenance** | [planner.ts](../web/src/lib/engine/planner.ts) documents goal recalibration fitted on frozen test users. [ml/evaluate.py](../ml/evaluate.py) computes refitted coefficients for a fit half but reports calibrated bins using the previously shipped constants. | Audit which users produced those constants; fit calibration on a separate calibration split and report on untouched test users. Do not describe the calibration improvement as fully independent until that provenance is established. |
| **P2: time and window correctness** | [analytics.ts](../web/src/lib/engine/analytics.ts) uses host-local dates and an end boundary of `anchor + 1 day`; other engine modules use Dhaka or UTC days. Monthly/near-midnight and future-dated entries need consistent treatment. | Standardize ledger-day conversion and add Dhaka midnight, month-end, future-entry and short-history tests before changing these calculations. |
| **P2: cold-start work** | [ml.ts](../web/src/lib/engine/ml.ts) trains/evaluates a logistic model once per process using the current date. That introduces request cold-start work and calendar-dependent outputs, unlike the versioned LightGBM artifacts. | Move training offline and ship versioned coefficients/metrics; measure cold and warm request latency on the deployment. |
| **P2: test coverage gaps** | The existing suites are strong for pure engines, but the goal-route 500 and missing liquidity propagation passed the original 95 web tests. No committed browser/device end-to-end suite covers the complete owner workflow. | Add route-level persistence tests and a short browser flow for onboarding → capture → edit → goal edit → liquidity update → forecast → reset. Include two-client authorization tests when auth is added. |
| **P2: operational repeatability** | App CI uses Bun `latest` and `bun install` without frozen mode. Python dev/transitive dependencies are partly unpinned. Dev/start scripts pipe to `tee`, which can mask the server's exit status. Android CI can generate an ephemeral signing key if the stable secret is absent. | Pin runtime versions, freeze installs, preserve command failure status, and fail release builds when stable signing credentials are missing. |
| **P2: documentation drift** | `context/context/progress-tracker.md` still says planning/pre-T+0, while code is implemented. Context standards describe static export and prohibit Next API routes, whereas the current app has server routes. CI test-count labels are outdated. | Treat current source and verified commands as authoritative for this review; reconcile the tracker, architecture documents and test counts in a separate documentation pass. |

## Strong points

1. **Financial calculations are separated from narration.** The app has real deterministic money, categorization, recurring-pattern, simulation and planner code; it does not give an LLM a money-transfer tool.
2. **Useful safety fallback.** Python and v1 chat support reviewed bilingual templates, input sanitization, slot substitution and rejection of ungrounded output. Provider failures do not need to break the financial screens.
3. **Meaningful ML tests.** The nine shipped LightGBM quantile models match Python prediction fixtures, with tests for leakage, recurring-income detection, path constraints and safe-to-spend behavior.
4. **Honest evaluation disclosures.** The README labels synthetic data and acknowledges the bootstrap comparison, rare-event limitations, missed recall target and goal-calibration optimism. Retain that candor when presenting results.
5. **Bangladesh-specific product work.** Bangla/Banglish capture, Bengali digit handling, bilingual explanations, cash-out fee auditing and irregular-income forecasting address concrete local needs.
6. **Runnable delivery paths.** There is a built standalone web app, a Python reference service, an Android release workflow, and an offline sample-data fallback with retry/error handling. Actual phone verification remains necessary.
7. **Broad existing validation.** Engine, API, model-parity and provider-fallback tests exercise real behavior; frozen installation, lint, types, build and live smoke checks now pass in this environment.

## Organization and next steps

Keep the current separation: `core/` for pure Python finance, `ml/` for offline model work, `api/` for the reference service, `web/src/lib/engine/` for TypeScript engines, `web/src/lib/server/` for persistence/context, and route handlers for request/response wiring. The highest-value reorganization is consolidating duplicated calculation/narration paths, not moving folders during a deadline.

For the remaining deadline window: freeze feature additions; review the small diff; demonstrate only synthetic data; run the demo phone's online and airplane-mode journeys; make the presentation distinguish the owner UI model from the v1 LightGBM model; and verify the submitted APK/video/README links. Schedule authenticated ownership and durable persistence before onboarding real customers.
