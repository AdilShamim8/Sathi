# `ml/` — Sathi ML Pipeline (offline training & evaluation)

This folder is the **ML factory** of the Sathi monorepo. It is the merged Sathi
Python repository (main + the `ml/06-eval` handoff branch, 7 commits) reorganized
as an offline pipeline. It is **not a second product**: the shipped app is the
Next.js app at the repo root, which serves the model this pipeline trains.

```
ml/  ── make train ──▶  ml/ml/artifacts/forecast/<version>/   (pipeline output)
                          │ promote (copy)
                          ▼
root ml-artifacts/forecast/  ──▶  served at runtime by src/lib/engine/lightgbm.ts
                                  (bit-identical to the Python booster, by test)
```

- **Runtime dependency: none.** Nothing in the Next.js app imports or executes
  this folder. You only need it to **retrain, re-evaluate, or regenerate** the
  model, the metrics, or the synthetic dataset.
- **Serving dependency: `ml-artifacts/` (repo root).** The app reads the trained
  boosters + calibration from there. `ml/ml/artifacts/` holds the pipeline's own
  current output (`fc-2026-09-30-15d8427d`, the same version promoted to the
  root) so `pytest` runs out-of-the-box; `make train` replaces it and updates
  its `latest.json`.

## Layout

| Path | Contents |
| :--- | :--- |
| `core/` | Deterministic financial engines (money, categorizer, recurring, simulation, planner, safe-to-spend, cashout, cash-on-hand v2, metrics, formatting, timeutils) |
| `ml/` | Training & evaluation: `train.py` (LightGBM 9-quantile ensemble), `calibrate.py` (conformal widening + Platt), `evaluate.py` (T1–T7 suite → metrics), `panel.py` (30 leakage-safe features), `inference.py`, `benchmark.py`, `report.py`, `audit_data.py` |
| `api/` | The reference FastAPI service (v1 contract twin: same envelopes, paisa ints, evidence blocks the Next.js `/api/v1/*` routes reproduce) |
| `llm/` | Fail-closed LLM layer: sanitizer, numeric validator, orchestrator, 13 templates × bn/en |
| `config/` | 7 YAML assumption files (fees, categories, risk bands, calendar, personas, thresholds, dataset) — every value is ported into the app's `sathiConfig.ts` |
| `data_gen/` | Seeded synthetic data generator (2,000 balanced users + 500-user drifted cohort) + demo-bundle generator |
| `data/` | The generated parquet panel + ground truth (regenerable via `make data`) |
| `tests/` | 78 pytest tests (core engines, API integration, data generator, forecast paths, income timing) |
| `docs/` | `rulebook.md`, `guideline.md`, `risks.md`, `assumptions.md`, `third_party.md` + `metrics/` — the generated eval.json / benchmark.json the test suite validates against (`make eval` regenerates them; the promoted copies served by the app live in root `docs/metrics/` + `src/data/`) |
| `sathi_config.py`, `Makefile`, `requirements*.txt` | Entry point, commands, dependencies |

## Quickstart

```bash
cd ml
pip install -r requirements.txt -r requirements-dev.txt   # dev adds shap + matplotlib
export DATABASE_URL=sqlite:///./data/sathi.db             # python side uses its own db
pytest -q                                                 # → 78 passed

make data     # (optional, ~15 min) regenerate the seeded synthetic dataset
make train    # (optional, ~15 min) train + calibrate the 9 quantile boosters
make eval     # (optional, ~10 min) rebuild docs/metrics/*.json + eval_report.md
make run      # the reference FastAPI service on :8000 (API-compat twin)
make lint     # ruff + mypy
```

## Outputs & the promote flow

`make eval` writes fresh metrics into `ml/docs/metrics/` and `ml/docs/eval_report.md`.
To serve a newly trained model / fresh metrics in the app, promote them to the
repo root (the "ML owner kit" flow — the app only ever reads the promoted copies):

1. `cp -r ml/ml/artifacts/forecast/<new-version>/ ../ml-artifacts/forecast/`
   and update `../ml-artifacts/forecast/latest.json` to `{"version": "<new-version>"}`
2. `cp ml/docs/metrics/eval.json ml/docs/metrics/benchmark.json ../docs/metrics/`
   and `../src/data/` (the files served by `/api/v1/me/benchmark`)
3. `cp ml/docs/eval_report.md ../docs/eval_report.md`

The parity guarantee is enforced by `tests/fixtures/lgb-predictions.json`
(generated with Python lightgbm 4.5.0): the TypeScript predictor must reproduce
the Python boosters exactly before a new version can be promoted.

## Why this exists

The hackathon rulebook forbids hand-typed metrics (§14/§15): every number in
`/api/v1/me/benchmark` and `docs/metrics/` must be generated by `ml.evaluate`
on the frozen, user-split dataset. This pipeline is also the post-hackathon
path to retraining on real-world data (`ForecastRecord` rows persisted by the
app are the future scoring set). See the root `README.md` §8c and
`docs/HACKATHON_COMPLIANCE.md` for the full story.
